# Runbook

Operational reference for everything in this repo. If you're trying to set up Obsidian sync for the first time, you want [obsidian/setup.md](obsidian/setup.md), not this file.

## Terraform state

State lives in a GCS bucket named `<project-id>-tfstate`, created once via [scripts/bootstrap-state-bucket.sh](../scripts/bootstrap-state-bucket.sh). The bucket has object versioning enabled and uniform bucket-level access. The bucket name is supplied at init time via `backend.hcl`, which is gitignored — the state's location is not in version control, only its shape.

The state can contain sensitive values (the CouchDB password is generated by Terraform via `random_password`). Treat the state bucket like a secret store: only your principal should have `roles/storage.objectAdmin` on it.

### Recovering from a corrupted apply

If a `terraform apply` is interrupted half-way and state is left inconsistent:

1. List state versions: `gsutil ls -a gs://<project>-tfstate/personal-infra/default.tfstate`. The `#<generation>` suffixes are the version IDs.
2. Inspect a prior version: `gsutil cat gs://<project>-tfstate/personal-infra/default.tfstate#<generation> | jq .serial`.
3. Restore: `gsutil cp gs://<project>-tfstate/personal-infra/default.tfstate#<generation> gs://<project>-tfstate/personal-infra/default.tfstate`.

State drift (real resource doesn't match what Terraform thinks) is recovered with `terraform plan` to identify, then either `terraform apply` to push state to match the plan, or `terraform import` to bring an out-of-band resource under management.

## Secrets

The CouchDB admin password is the only secret managed here right now. The flow:

1. Terraform's `random_password.obsidian_couchdb_password` generates 32 alphanumeric characters at apply time.
2. The value is written to Secret Manager as `obsidian-couchdb-password`.
3. The VM's service account has `roles/secretmanager.secretAccessor` scoped to that one secret — not project-wide.
4. Cloud-init pulls the secret via `gcloud secrets versions access` on first boot and writes `/opt/obsidian/.env` (mode 0600).

The password is in Terraform state because `random_password.result` is stored. It's NOT in `terraform output` — there's no output exposing it directly. To retrieve the password from anywhere with appropriate IAM:

```
gcloud secrets versions access latest --project=<project> --secret=obsidian-couchdb-password
```

The repo never sees the password. `terraform.tfvars` doesn't either.

The Cloudflare API token IS in `terraform.tfvars` (gitignored). Treat that file like a credential — don't commit it, don't share it. If it leaks, rotate at https://dash.cloudflare.com/profile/api-tokens.

The CouchDB E2EE passphrase the LiveSync plugin will use is a separate secret you'll generate during client setup. **Save it to a password manager.** It's not stored anywhere recoverable on the server — losing it means re-bootstrapping the vault from scratch.

## Adding a new project to this repo

The repo is structured to grow. To add a project — call it `<proj>`:

1. **Terraform**: create `terraform/<proj>.tf`. Reuse the `random` and provider blocks already configured in `main.tf`. Use a section header comment to mark resource groupings. Prefix all resource names with the project name (`google_compute_instance.<proj>_...`) so multi-project state is readable.
2. **Variables**: add project-specific vars to `variables.tf` under a section header (`# ─── <proj> ───`). Add defaults to `terraform.tfvars.example`.
3. **Outputs**: add to `outputs.tf` under the same section header convention.
4. **Scripts**: create `scripts/<proj>/` for any cloud-init, helper scripts, or one-time setup. Source `scripts/lib/common.sh` for logging.
5. **Docs**: create `docs/<proj>/` with at least `setup.md`. Mirror the structure under `obsidian/` if relevant.
6. **README**: add the project under "Current projects" with a one-line description and a pointer to its setup doc.

State stays in the same bucket — adding a project doesn't need a separate bucket.

## Destroying everything

To tear it all down:

```
terraform -chdir=terraform destroy
```

That removes the VM, the service account, both secrets and their IAM bindings, and the Cloudflare DNS record. It leaves behind:

- The GCS state bucket (intentionally — destroy that manually if you really mean it: `gsutil rm -r gs://<project>-tfstate`).
- The enabled GCP APIs (`disable_on_destroy = false` on the `google_project_service` resources, so `destroy` doesn't yank them out from under anything else in the project).
- The Cloudflare tunnel resource itself (was created manually outside Terraform). Delete on the VM with `cloudflared tunnel delete obsidian` after stopping the systemd service: `sudo systemctl stop cloudflared && sudo systemctl disable cloudflared`.
- The local `~/.cloudflared/cert.pem` on the VM (delete the VM and it goes with it, but if you preserved the disk somehow, scrub it).
- Anything in the Obsidian vault data on the VM disk — gone with the disk when the VM is destroyed, *unless* you snapshot first.
