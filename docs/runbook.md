# Runbook

Operational reference for everything in this repo. If you're trying to set up Obsidian sync for the first time, you want [obsidian/setup.md](obsidian/setup.md), not this file.

## Terraform state

State lives in a GCS bucket named `<project-id>-tfstate`, created once via [scripts/bootstrap-state-bucket.sh](../scripts/bootstrap-state-bucket.sh). The bucket has object versioning enabled and uniform bucket-level access. The bucket name is supplied at init time via `backend.hcl`, which is gitignored — the state's location is not in version control, only its shape.

The state can contain sensitive values (the CouchDB password is generated by Terraform via `random_password`). Treat the state bucket like a secret store: only your principal should have `roles/storage.objectAdmin` on it.

### Recovering from a corrupted apply

If a `terraform apply` is interrupted half-way and state is left inconsistent:

1. List state versions: `gsutil ls -a gs://<project>-tfstate/personal-infra/default.tfstate`. The `#<generation>` suffixes are the version IDs.
2. Inspect a prior version: `gsutil cat gs://<project>-tfstate/personal-infra/default.tfstate#<generation> | jq .serial`.
3. Restore: `gsutil cp gs://<project>-tfstate/personal-infra/default.tfstate#<generation> gs://<project>-tfstate/personal-infra/default.tfstate`.

State drift (real resource doesn't match what Terraform thinks) is recovered with `terraform plan` to identify, then either `terraform apply` to push state to match the plan, or `terraform import` to bring an out-of-band resource under management.

## Secrets

Nine secrets exist in Secret Manager once all three phases are deployed.

**Phase 1 (Obsidian sync)**:

1. `obsidian-couchdb-password` — Phase 1 admin password. Generated by Terraform (`random_password`). The VM service account reads it on first boot.

**Phase 2 (Obsidian MCP)**:

2. `obsidian-mcp-couchdb-password` — Password for the scoped CouchDB user the MCP server uses. Generated by Terraform. Provisioned into CouchDB by `scripts/obsidian-mcp/create-couchdb-user.sh`.
3. `obsidian-livesync-passphrase` — The E2EE passphrase you typed into the Obsidian LiveSync plugin during Phase 1 client setup. **Populated out of band** (`gcloud secrets versions add …`) — Terraform creates the secret resource with `lifecycle.ignore_changes` on the version so it doesn't clobber the real value. The MCP service account is the only principal with read access. The vault-indexer also reads it (Phase 3).
4. `obsidian-mcp-oauth-signing-key` — RSA-2048 PKCS#8 PEM the OAuth server uses to sign every JWT it issues (auth codes, access tokens, refresh tokens, the Google round-trip state). Generated out of band by `scripts/obsidian-mcp/generate-oauth-key.sh`. Rotating it invalidates every issued token (clients re-auth) — that's the recovery path on suspected token compromise.
5. `obsidian-mcp-google-oauth-client-secret` — The client secret half of the Google OAuth 2.0 Web application client used as the OIDC IdP for the human-auth step at `/authorize`. Created in GCP Console → APIs & Services → Credentials and pushed to Secret Manager out of band.

**Phase 3 (Vault indexer)**:

6. `vault-indexer-search-token` — Shared bearer between the MCP server and the indexer's `/search` endpoint. Generated by Terraform (`random_password`). Read by both the VM SA (writes it into `/opt/vault-indexer/.env`) and the MCP service account (sends it as `Authorization: Bearer …`). Rotating it: re-run `terraform apply` (regenerates the random_password) and then `scripts/vault-indexer/deploy.sh` (which rewrites `/opt/vault-indexer/.env`). The MCP picks up the new value at its next cold start.
7. `vault-indexer-openai-key` — Optional. Required only when the indexer is configured with `EMBEDDER=openai-small` or `EMBEDDER=openai-large` (primarily the evaluation harness). **Populated out of band** with the same `lifecycle.ignore_changes` pattern as the LiveSync passphrase. Leave as the placeholder if you never run a hosted-model comparison.
8. `vault-indexer-cf-access-client-id` — Cloudflare Access service token client_id, written by Terraform from the `cloudflare_access_service_token.mcp_to_indexer` resource. Read by the MCP service account, sent as `CF-Access-Client-Id` header on every `/search` call. Rotating it: `terraform taint cloudflare_access_service_token.mcp_to_indexer && terraform apply` rolls both halves of the token in one step.
9. `vault-indexer-cf-access-client-secret` — The other half of the CF Access service token. Same lifecycle as #8.

The Google OAuth client ID is in `terraform.tfvars` (`google_oauth_client_id`) — it's not sensitive on its own; the matching secret is. The email allow-list (`mcp_allowed_emails`) is also in tfvars, set as a Cloud Run env var.

All `random_password` values are in Terraform state because `result` is stored. None are exposed via `terraform output`. To retrieve any of them with appropriate IAM:

```
gcloud secrets versions access latest --project=<project> --secret=<secret-id>
```

The repo never sees these values. `terraform.tfvars` only contains the Cloudflare API token (still gitignored).

### Cloudflare API token: required permissions

The `cloudflare_api_token` in `terraform.tfvars` is the one credential the repo references that lives outside Secret Manager. Its required permissions grew between phases — if you provision it once for Phase 1 and forget about it, Phase 3 will fail with `Authentication error (10000)` on the Access resources.

Cumulative permissions across all phases:

| Permission | Scope | Added in |
|---|---|---|
| `Zone:Read` | Zone (your domain) | Phase 1 |
| `DNS:Edit` | Zone (your domain) | Phase 1 |
| `Access: Apps and Policies:Edit` | Account | Phase 3 |
| `Access: Service Tokens:Edit` | Account | Phase 3 |

Account Resources must include the account that owns the zone (Account-scoped permissions can't be granted on a zone-only token). Zone Resources can stay restricted to the specific domain.

Editing the token's permissions is non-destructive (no value rotation). Cloudflare dashboard → **My Profile → API Tokens** → edit. If you'd rather create a new token, paste the value into `terraform.tfvars` and re-apply.

The CouchDB E2EE passphrase you typed into LiveSync during Phase 1 setup is **unrecoverable** if you lose it from your password manager AND from the `obsidian-livesync-passphrase` Secret Manager entry. Losing it means re-bootstrapping the vault from scratch.

## Adding a new project to this repo

The repo is structured to grow. To add a project — call it `<proj>`:

1. **Terraform**: create `terraform/<proj>.tf`. Reuse the `random` and provider blocks already configured in `main.tf`. Use a section header comment to mark resource groupings. Prefix all resource names with the project name (`google_compute_instance.<proj>_...`) so multi-project state is readable.
2. **Variables**: add project-specific vars to `variables.tf` under a section header (`# ─── <proj> ───`). Add defaults to `terraform.tfvars.example`.
3. **Outputs**: add to `outputs.tf` under the same section header convention.
4. **Scripts**: create `scripts/<proj>/` for any cloud-init, helper scripts, or one-time setup. Source `scripts/lib/common.sh` for logging.
5. **Docs**: create `docs/<proj>/` with at least `setup.md`. Mirror the structure under `obsidian/` if relevant.
6. **README**: add the project under "Current projects" with a one-line description and a pointer to its setup doc.

State stays in the same bucket — adding a project doesn't need a separate bucket.

## Destroying everything

To tear it all down:

```
terraform -chdir=terraform destroy
```

That removes both phases at once: the VM, the Cloud Run service, the domain mapping, the Artifact Registry repo, all five secrets and their IAM bindings, both Cloudflare DNS records, the service accounts. It leaves behind:

- The GCS state bucket (intentionally — destroy that manually if you really mean it: `gsutil rm -r gs://<project>-tfstate`).
- The enabled GCP APIs (`disable_on_destroy = false` on the `google_project_service` resources, so `destroy` doesn't yank them out from under anything else in the project).
- The Cloudflare tunnel resource itself (created manually outside Terraform). Delete on the VM with `cloudflared tunnel delete obsidian` after stopping the systemd service: `sudo systemctl stop cloudflared && sudo systemctl disable cloudflared`.
- The Google OAuth 2.0 client (created manually in GCP Console → APIs & Services → Credentials). Delete from there if you want to fully clean up.
- The local `~/.cloudflared/cert.pem` on the VM (delete the VM and it goes with it).
- Anything in the Obsidian vault data on the VM disk — gone with the disk when the VM is destroyed, *unless* you snapshot first.

To destroy ONLY Phase 3 (vault-indexer) and keep Phases 1+2 intact:

```
terraform -chdir=terraform destroy \
  -target=google_artifact_registry_repository.vault_indexer \
  -target=google_secret_manager_secret.vault_indexer_search_token \
  -target=google_secret_manager_secret.vault_indexer_openai_key \
  -target=google_secret_manager_secret.vault_indexer_cf_access_client_id \
  -target=google_secret_manager_secret.vault_indexer_cf_access_client_secret \
  -target=cloudflare_access_policy.indexer_allow_service_token \
  -target=cloudflare_access_service_token.mcp_to_indexer \
  -target=cloudflare_access_application.indexer \
  -target=cloudflare_record.indexer
```

Then on the VM, stop and remove the indexer container and its data dir:

```
gcloud compute ssh <vm> --command 'cd /opt/obsidian && sudo docker compose stop vault-indexer && sudo docker compose rm -f vault-indexer'
gcloud compute ssh <vm> --command 'sudo rm -rf /opt/vault-indexer'
```

Also remove the indexer ingress rule from `~/.cloudflared/config.yml` on the VM. The Phase 2 MCP server's env vars will still reference the (now-deleted) secrets after a destroy; either redeploy the MCP after `terraform apply` re-creates them, or accept that the indexer arm will fail and `search_notes` will silently degrade to lexical-only.

To destroy ONLY Phase 2 and keep Phase 1 (the vault) running:

```
terraform -chdir=terraform destroy \
  -target=google_cloud_run_v2_service.obsidian_mcp \
  -target=google_cloud_run_domain_mapping.mcp \
  -target=google_artifact_registry_repository.obsidian_mcp \
  -target=google_secret_manager_secret.obsidian_mcp_couchdb_password \
  -target=google_secret_manager_secret.obsidian_livesync_passphrase \
  -target=google_secret_manager_secret.obsidian_mcp_oauth_signing_key \
  -target=google_secret_manager_secret.obsidian_mcp_google_oauth_client_secret \
  -target=google_service_account.obsidian_mcp \
  -target=cloudflare_record.mcp
```

The Google OAuth client lives outside Terraform — delete it manually from GCP Console if you want to fully clean up.
